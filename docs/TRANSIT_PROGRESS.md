# 0.0.90：小窗可见尺寸与中转卡片

“桥接与自动化 → 跳转行为 → 显示中转卡片”默认关闭，开启后才显示系统中转卡片；关闭不影响解冻、原始点击接管和目标跳转。切换设置会使旧的系统确认失效，等待当前配置重新保存并确认后再冻结 IceBridge。关闭生效后立即收起已有卡片，关闭期间的排队阶段不会重新弹出窗口。

同组的“小窗打开”是独立开关，默认关闭，仅作用于“小窗应用”中勾选的普通链接目标，空名单不使用小窗。选定目标可以在不显示卡片时请求系统小窗，也可以显示卡片并按普通方式打开；支付和原页面回退不改小窗参数。使用范围和系统限制见 [独立运行说明](AUTONOMOUS_RUNTIME.md)。

“规则内统一打开”默认开启；关闭后仅接管冻结目标，已启用目标保留原流程，也不会仅因为被勾选为小窗应用而强制接管。

小窗事务使用约 156 × 72 dp 卡片、27 dp 图标，卡片按目标任务的可见边界保持中心，并按实际空间等比缩小；MIUI 原生缩放可读取时也参与边界换算。窗口尚未确定时才暂用保存的请求范围；已存在的小窗先查询唯一可见的同包任务，再由本次启动 token 确认。普通事务保留 208 × 96 dp，两种模式均只有图标和流线，目标首窗出现就收起。

“小窗尺寸与位置”改为真实屏幕上的透明线框调节器，拖动和缩放线框时，原生卡片预览跟随其中心；保存后调节层隐藏，取消或返回不保存。调节器不再绘制缩小的手机示意图，不需悬浮窗权限，不启动目标应用。

`Task.onConfigurationChanged` 后只读取不可变边界快照；MIUI 缩放从当前 Task 所属的本地 ATMS／原生栈读取，不在 WM 全局锁中调用 Binder、Provider 或包管理器。UI 仅接受当前交易、用户、包和任务实例一致的更新；临时锚点不会阻止精确 token 改绑，任务身份使用弱键保持稳定，旧事件不复活已关闭卡片。尚未核实仅改变 Surface、没有 Task 配置回调的厂商动画入口，因此不能保证逐帧跟随这类移动或缩放。

`LSPosed_20261016_082748.zip` 与两张截图确认：手机收到的逻辑启动边界是 `Rect(347,315 - 1369,1644)`，与调节线框一致，但 `ActivityOptionsInjector` 的缩放值未指定（`-1`），原生栈随后应用 `freeFormScale=0.7`。可见宽高从 `1022 × 1329` 缩到约 `715 × 930`，左上角基本不变，正是实际小窗比预览小的原因。0.0.90 在所选链接目标的单次启动参数中，通过可选 `getActivityOptionsInjector().setFreeformScale(1f)` 显式请求不再额外缩放；接口缺失或不可用时保留原生自由窗口请求。没有硬编码除以 0.7，也不修改全局小窗设置。已有任务的卡片边界则按读取到的原生缩放换算，不能把逻辑 Task bounds 直接当作屏幕可见大小。

反射接口依据是 [HyperCeiler 的启动参数与原生栈读取](https://github.com/ReChronoRain/HyperCeiler/blob/main/library/libhook/src/main/java/com/sevtinge/hyperceiler/libhook/rules/systemframework/freeform/StickyFloatingWindows.java)，缩放参数回读及可见边界处理另参照 [FanFreeform 的 HyperOS 桥接实现](https://github.com/oxohang/FanFreeform/blob/main/app/src/main/java/com/oxohang/fanfreeform/xposed/HyperOsFreeformBridge.java)。这些源码可确认接口使用方式；设置 1.0 能在本机 ROM 恢复线框尺寸，是结合手机日志作出的修复判断，仍需安装新版并重启后实测，不能以模拟器结果代替。

首次安装／升级带此开关的版本需要重启手机加载新的 system_server 模块；随后单独切换该开关无需重启。修改设置需先解冻本体，系统确认后再冻结。偏好会随独立运行配置持久保存，重启恢复时仍遵循该开关；schema 8／codec 1 的旧数据缺少此字段时默认关闭，同时保留主题、全部规则、在线缓存和版本高水位。

普通全屏事务使用约 208 × 96 dp 的居中小卡片，只显示两个 36 dp 应用图标与蛇形流线，没有箭头、应用名、状态文字或品牌文字；小窗事务使用上面的紧凑尺寸。解冻／打开阶段和应用名称只保留在无障碍描述中。本体被冻结时，卡片由系统侧原生窗口显示，不启动本体 Activity，也不解冻本体。普通模式保留原来的桥接页面。

一条带渐变尾迹的亮色线段绕过来源图标，沿曲线流向目标，再绕过目标图标；按路径距离匀速移动，切换解冻／打开阶段时保持同一个绘制视图。应用图标和无障碍名称由系统包管理器读取，未知来源使用通用应用图标，不冒充具体应用。图标查询缓存有数量上限，动画逐帧不查询包管理器。

动画只在卡片可见时运行；收起、脱离窗口后停止，系统关闭动画时显示静态流线。卡片继续沿用同色系的明暗配色、原有超时与触摸穿透规则，不改变跳转请求的参数。

## 接管原始点击

0.0.85 对独立模式中已识别的微信／QQ 普通 WebView 点击增加独占接管。0.0.88 将匹配的已启用目标统一纳入模块路径，不再受旧“仅冻结应用”设置限制；冻结时仍须确认可解冻。已审核的微信／QQ 点击和干净的隐式 HTTP(S) `ACTION_VIEW`，确认来源身份、前台状态和唯一目标后，先阻止原请求，再执行目标路由，不让原页面与目标应用同时启动。

框架外层 `ActivityStarter.execute` 仍完整执行并清理；只有本次已认领的内层请求使用框架原生 `START_ABORTED` 路径，动画 options 的取消也只执行一次。包查询和准备在全局锁外，解冻与目标启动在外层结束后交给工作线程。

该处理对应 [AOSP Android 16 的 ActivityStarter](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/services/core/java/com/android/server/wm/ActivityStarter.java)：原生中止结果不会当作新 Activity 成功创建，外层仍完成 metrics、URI 记录和回收，并将中止结果转换成调用方可接受的返回值。实际安装时还会检查该 ROM 的返回映射和必要字段；不符合时保留原流程。

规则或配置在排队期间变更、目标启动失败、工作线程无法接收任务时，事务最多尝试一次原始回退。原来源的私有 extras 只回到同一来源组件，目标应用仍只收到审核过的公开 URL。支付、真实结果请求、URI 授权、无法确认身份或不支持的框架请求保留原行为，不再通过另起目标的方式并行补偿。

这是启动请求层的接管；已有 WebView 内部直接加载、没有新 Activity 请求的链接仍不在该入口的观察范围。真实 ROM 的 Hook、前台应用返回栈和失败回退仍需手机复测。

升级后重启设备，保持本体解冻，等待系统重新确认配置，再冻结本体。卡片沿用同步的主题色与明暗偏好；选择跟随系统时，按系统当前日夜模式取色。卡片仅用于模块实际接管的事务，正常网页、无匹配规则或未接管的已启用目标不会出现提示。

## 显示与关闭

- 确定唯一且可解冻的目标后显示卡片；状态回读确认可用后进入打开阶段。已启用目标被允许接管时直接进入打开阶段，页面上不显示阶段文字。
- 目标的系统启动画面或应用主窗口首次实际展示时立即收卡，不再等待最终内容首帧或网络加载。提交启动接口本身仍不作为窗口已展示的证据，没有最短显示时间。
- 成功的 `WindowState.performShowLocked` 后置回调检查窗口类型、隐藏状态、用户和活动可见性；后台绘制、其他用户与旧事务事件不会误收卡。原有热重用回调仍受可见性和已绘制状态约束。
- 热重用关联新投递的 Intent；多级路由丢失额外标记时，按同包、同用户、打开阶段和事件时间关联目标实际窗口。
- 老事务的绘制、超时和失败不能关闭更新的卡片。权限弹窗只中断进度提示，不当作目标内容页打开成功。
- 卡片不抢焦点，不接收触摸，不铺全屏遮罩。切用户、锁屏、Home／最近任务、失败及 12 秒超时会收起；后端不会等待卡片或动画。
- 支付 SDK 原始调用链继续直通，不额外插入卡片、等待或结果回放。

明暗卡片使用同一颜色种子与不同深浅的底色。配置保持 schema 8／codec 1，旧存储缺少新主题字段时使用蓝色与跟随系统，保留全部规则、在线缓存和版本高水位。

## 0.0.85 日志中的收卡问题

`LSPosed_20261015_220511.zip` 中，两次微信到抖音的接管都成功，各启动目标一次，没有原微信 WebView 并行启动、回退、解冻失败或本轮模块崩溃。卡片确实会关闭，但选错了关闭边界：

| 样本 | 捕获到启动提交（模块计时） | 捕获到目标启动画面 | 目标启动画面到卡片 Surface 隐藏 |
| --- | ---: | ---: | ---: |
| 第一次 | 114 ms | 463 ms | 9480 ms |
| 第二次 | 219 ms | 318 ms | 8833 ms |

旧实现等待最终 DetailActivity 内容绘制，因而长时间覆盖已经打开的目标启动页。0.0.86 改用成功展示的起始／应用窗口信号；目标呈现回调已在 UI 线程时直接处理收卡，但 Home 等取消仍保持原队列顺序，防止取消越过已排队阶段后卡片重新出现。

依据为 [AOSP Android 16 WindowState.performShowLocked](https://android.googlesource.com/platform/frameworks/base/+/android-16.0.0_r1/services/core/java/com/android/server/wm/WindowState.java#3956)。仅 `onStartingWindowDrawn` 并不等同于展示已经成功，因此使用成功返回后的窗口事件。

日志中“收卡日志到 Surface 隐藏”另有 333／351 ms。它不能证明整段时间都完全不透明；[AOSP 的动画资源加载逻辑](https://android.googlesource.com/platform/frameworks/base/+/android-16.0.0_r1/core/java/com/android/internal/policy/TransitionAnimation.java#293)在 `windowAnimations=0` 时本来就不加载样式动画，不能据此认定是本模块忘记关闭动画，也不能承诺覆盖 ROM 的退场策略。系统 UI 线程还出现 112～300 ms 派发耗时，没有对照或栈，不能全部归因于流线绘制。

另发现开机首次 observer／Provider 调用失败后，固定等一分钟才再次初始化。现在按 2／4／8／15／30／60 秒退避，成功后恢复一分钟周期，异常也不会中断原有单一刷新循环。旧日志只记录异常类名，不能确定具体空对象；新版增加脱敏首栈位置，不输出异常 message、URL 或 SDK 参数。

## 历史日志中的速度差异

输入为 `LSPosed_20261015_165300.zip`。六次目标主进程都重新创建，均为冷启动；日志没有热启动对照。下面只列脱敏时长，不记录实际链接。

| 目标样本 | 捕获到启动调用返回 | 捕获到目标首帧 |
| --- | ---: | ---: |
| 抖音第一次 | 172 ms | 未记录；后续 Activity 被销毁，不能推算成功 |
| 抖音第二次 | 153 ms | 5339 ms |
| YouTube | 163 ms | 2468 ms |
| 酷安 | 389 ms | 无目标首帧；5670 ms 出现权限窗口 |
| X | 130 ms | 3562 ms |
| 小红书 | 117 ms | 4374 ms |

本份日志可确认，秒级差异主要在模块启动调用之后。它包含目标进程初始化及应用内部路由，无法进一步证明某个网络请求、第三方模块或模块队列是根因。原微信 WebView 和目标曾同时启动，可能增加负载，但没有对照组，不能把这一点写成已证实的性能原因。

新版本不会给较快的应用加固定延迟来统一观感，也不承诺不同应用或网页拥有相同的冷启动速度。它补足等待反馈与阶段计时，便于继续定位真正慢的环节。

## 分段日志

`transit timing` 每笔事务使用独立 id，记录以下阶段：

- `worker-start`：工作线程开始。
- `thawing`：开始修改目标状态。
- `opening`：状态可用，准备调用启动接口。
- `submitted`：启动接口成功返回。
- `target-visible-starting-window`：目标系统启动画面已展示，结束中转提示。
- `target-visible-app-window`：应用窗口已展示，或已有可见绘制窗口恢复。
- `system-prompt`：出现系统权限窗口，仅收起提示，不表示目标已完成。

`elapsedMs` 从捕获开始计算；`sourceStartMs` 记录原请求继续执行到入队的时间；`queueMs` 记录入队等待；`workerMs` 从工作线程开始计算；`thawMs` 为解冻到打开阶段的时长。没有发生的阶段用未测值表示，不伪造零耗时。日志只包含事务 id、用户、包名和时长，不写原 URL、剪贴板或 SDK 参数。

“窗口可见”不同于网页数据加载完成：应用自己的启动页、权限、登录和网络加载由目标应用继续完成；此时中转卡片已经收起。

## 验证边界

回归包括阶段顺序、重复和失败不误报、观察器异常不影响后端、新旧事务隔离、冷绘制标记更新顺序、无标记多级路由、热重用、权限提示、日夜配色与原生窗口焦点／触摸。

debug 的非导出预览 Activity 使用 Activity 子窗口，复用相同卡片布局与显示状态；它验证原生渲染，不等同于真实 system_server 的系统窗口权限。生产使用 system_server classloader 获取 UiThread，以及 TYPE_SYSTEM_DIALOG；Android 12 起同时设置 trusted overlay。API 36 独立 app_process 未登记为 AMS 应用进程，不能代替系统窗口验收；当前模拟器平台证书也不匹配公开 AOSP 开发平台证书，因此未尝试安装系统 UID 宿主或修改系统权限。

输入回归等待真实焦点、布局和输入事务后注入点击，并确认背景收到 DOWN 和点击回调。测试需要访问 `UiAutomation.syncInputTransactions()` 测试接口，可以仅对 instrumentation 进程执行：

```powershell
adb -s emulator-5556 shell am instrument --no-hidden-api-checks -w -r io.github.yudigaga.icebridge.test/androidx.test.runner.AndroidJUnitRunner
```

该参数不修改设备全局隐藏 API 策略，也不用于正式应用。

本次手机日志中，五次微信到抖音请求均由模块成功接管，每次只有一次目标启动记录，卡片均因目标窗口显示而关闭；其中三次解冻、两次目标已启用。日志同时确认了 0.0.89 的厂商 0.7 缩放问题，不是 0.0.90 修复已通过的证据。新版的线框与窗口尺寸、已有小窗的卡片中心及厂商约束仍需手机复测。最终构建与设备结果见 [RELEASE_VALIDATION.md](RELEASE_VALIDATION.md)。原始日志、数据库及本地采样不提交仓库。
